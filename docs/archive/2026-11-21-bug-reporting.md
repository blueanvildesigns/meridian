# Decisions: bug reporting (2026-11-21)

Source: the owner's brief for in-app bug reporting, 2026-11-21. Built in two phases, each its own commit, so Phase 1 can ship alone. Owner steps: `docs/manual-setup-bug-reporting.md`.

## Phase 1: GitHub issue form and an in-app link (no backend)

1. **Issue form** `.github/ISSUE_TEMPLATE/bug_report.yml`: Summary (required), What happened (required), Expected behavior (required), Steps to reproduce, Diagnostics (optional, rendered as a text block). Default label `bug`. `config.yml` turns blank issues off. The form tells reporters that issues are public.
2. **"Report a bug" link** in the footer (between About and Support on Ko-fi) and in a new About section, "Found a bug?", placed before Credits. **No board draws either one**, so both copy their neighbours: the footer's link style and About's section style. The owner should confirm the placement and wording (BR-1 in `docs/decisions-log.md`).
3. **The link opens** `https://github.com/blueanvildesigns/meridian/issues/new?template=bug_report.yml&diagnostics=…` in a new tab. The repo comes from `git remote`. The diagnostics are six lines: app version and commit, user agent (capped at 256 characters), OS name (no version), IANA time zone, time format setting (with what "Browser default" resolves to), and locale.
4. **Privacy.** The diagnostics are built from the browser's own facts plus the time format setting only; the function has no access to saved cities. Nothing leaves the browser until the reporter submits the form on GitHub, where every field is visible and editable.
5. **Length.** Links are capped at 2,000 characters. If a link would be longer, fields are shortened with an ellipsis in this order: steps, what happened, summary, diagnostics. A real set of diagnostics is about 400 characters encoded.
6. **Triage workflow** `.github/workflows/issue-triage.yml`: on every new issue, add `needs-triage` and comment "Thanks for the report! We'll take a look." It uses `gh` with the workflow token (`issues: write` only), never checks out code, and passes only the issue number to the shell, so no issue text can inject commands.
7. **Prefill keys** are the form's field ids (`summary`, `what-happened`, `steps`, `diagnostics`). GitHub documents a field's `id` as its key for URL prefills; changing an id breaks the app's link.

## Phase 2: in-app form, no GitHub account needed

Checked against Firebase's docs on 2026-11-21 (get-started, config-env, hosting/functions, App Check reCAPTCHA Enterprise and debug provider, manage-functions, pricing). Where the docs were silent, it says so.

8. **Dialog** (`webapp/src/ui/bugReport/`): What went wrong (required, 2,000 characters), Steps to reproduce (optional, 2,000), Email (optional, 254), Include diagnostics (ticked by default, showing the exact text sent; unticked sends none), a hidden honeypot field (`website`), a standing amber note that issues are public, and a reCAPTCHA notice with Google's privacy and terms links. Native modal `<dialog>` (focus trap, Esc, focus returns), labelled fields, errors tied to fields with `aria-describedby`, the success line focused and in a status region, failures in an alert. Not drawn: it follows Settings and About. Axe finds nothing in light and dark, wide and phone, in the form, error and failure states (checked by hand against the dev server, not in the e2e suite: see 21).
9. **Opening it.** With the four Firebase settings in the build (`webapp/.env.example`), the footer's "Report a bug" becomes a button and About gets a "Report a bug" button (About closes first). Without them, both stay phase 1's GitHub link, so users see no change until the settings are committed. The Hosting rewrite in `firebase.json` is another matter: merge phase 2 only after the function is deployed (owner part 5), or the live Hosting deploy may fail looking it up.
10. **Privacy model kept.** Nothing is sent, and nothing third-party loads, until Send. Send loads the Firebase SDK (one lazy 12.8 KB-gzip chunk) and Google's reCAPTCHA Enterprise script, fetches one limited-use App Check token, then posts. Token auto-refresh is off. **This is new for Meridian: a request to Google**, which sees the reporter's IP address and browser signals. The dialog says so before Send, About's "Your data" line and the root README now mention bug reports, and reCAPTCHA's badge is hidden as Google allows when the form carries that notice. The owner should confirm this tradeoff (BR-5).
11. **App Check provider: reCAPTCHA Enterprise.** Firebase's reCAPTCHA v3 page (non-English versions) says new integrations should use Enterprise; the English page is less direct. Enterprise is score-based, with a free monthly quota of assessments, then billed. The docs page doesn't state the quota number, so check the reCAPTCHA pricing page.
12. **CSP** gains exactly what App Check needs, found by reading the SDK and Google's reCAPTCHA FAQ: `script-src` `https://www.google.com/recaptcha/` `https://www.gstatic.com/recaptcha/`; `connect-src` `https://content-firebaseappcheck.googleapis.com` `https://www.google.com/recaptcha/`; `frame-src` `https://www.google.com/recaptcha/` `https://recaptcha.google.com/recaptcha/`. Everything else stays `'self'`. A forum report says reCAPTCHA may want more `connect-src` hosts; and `style-src 'self'` may block styles reCAPTCHA injects. **Not verified with a real key**: check a preview channel's console for CSP violations on Send (owner step 6.3).
13. **Function** `reportBug` (`functions/`): Cloud Functions for Firebase 2nd gen, TypeScript, Node 22 (the Firebase docs list 20 and 22; Cloud Run lists 24 as GA, but Firebase's pages don't yet), `us-central1` (one of the regions Firebase recommends for Hosting rewrites), `maxInstances: 1`, `concurrency: 80`, 256 MiB, 30 s timeout (Hosting cuts requests at 60 s), public invoker (Hosting calls it anonymously), its own service account `report-bug@…` with only Firestore user, App Check token verifier and access to its one secret.
14. **Request flow:** POST only (405), JSON only (415), body ≤16 KB (413), Origin must be the live site, a Firebase domain or a preview channel when present (403), off switch (503), 5 an hour per address (429), App Check token required and consumed (401), the token not used before by our own record (401; item 24), fields validated (400; honeypot hits get `rejected`), 30 issues an hour in all (429 `busy`), then GitHub (502 on failure). Responses carry a code and a friendly message; the web app shows its own text per code.
15. **Sanitizing.** NFC, newlines normalised, control and bidi-override characters removed, blank-line runs collapsed, lengths counted in code points after cleaning. Every user field goes inside a fenced code block whose fence is longer than any backtick run in it, so mentions, cross-references, links, images and HTML render as plain text. Titles are `[Bug]: ` plus the first line, 80 characters.
16. **Rate limits: in memory, not Firestore.** Tradeoff: free, no setup, no latency, but per instance and forgotten on a cold start. `maxInstances: 1` makes it effectively global while warm. A Firestore counter would survive restarts but add a read and write per report, and couldn't stop a determined attacker either. **The per-address key is the X-Forwarded-For entry Google's front end vouches for** (item 25): the last entry, or, when that's one of Hosting's own addresses, the visitor Hosting names in front of it. The limit still only slows casual repeats (anyone with many addresses gets many limits); App Check with replay protection is the real defence, and the global cap bounds the damage.
17. **Token:** fine-grained PAT, repository access "Only select repositories" → this repo, permission Issues: Read and write (Metadata: read is added automatically), stored as Secret Manager secret `GITHUB_BUG_TOKEN` via `firebase functions:secrets:set`. A redeploy is needed after changing it (Firebase docs). Issues created this way show the PAT owner as author. A GitHub App would avoid that and expiry, at the cost of more setup; not done.
18. **Reporter email: never in the issue.** Stored in Firestore `bugReportContacts/{issueNumber}` (`email`, `issueNumber`, `issueUrl`, `createdAt`, `expireAt`), written by the function through the Admin SDK. `firestore.rules` denies every client read and write. `expireAt` is 180 days on, for a TTL policy (owner step 4.4). The issue says only whether an email was left. If saving fails, the issue still stands and the reply says `contactSaved: false`. Read them in the Firebase console → Firestore → `bugReportContacts`.
19. **Fallback.** Any failure (spam check didn't load, network, any error code) shows "Your report wasn't sent" and a link to GitHub's form with summary, what happened, steps and (if ticked) diagnostics filled in, never the email. "Use GitHub instead" is always in the dialog's footer.
20. **Params** (`functions/.env`, committed): `BUG_REPORT_REPO`, `BUG_REPORT_ENABLED` (off switch on next deploy). The emulator skips App Check (only when `FUNCTIONS_EMULATOR` is set), and with `GITHUB_BUG_TOKEN=dry-run` in `functions/.secret.local` it skips GitHub. It refuses to save contacts unless the Firestore emulator is running.
21. **Tested:** 79 function unit tests (validation, sanitizing, issue body, rate limits, GitHub call with a mocked fetch, the whole handler with mocked dependencies); web unit tests for the client and dialog; the e2e suite (Chromium, Firefox, mobile; WebKit in CI); `functions/scripts/emulator-smoke.sh` through the Hosting emulator's real rewrite (8 checks plus the private contact document); the dialog against the emulator in a browser. **Not tested:** anything on real Firebase (deploy, App Check with a real key, reCAPTCHA under our CSP, Secret Manager, Firestore TTL, IAM), a real GitHub issue from the function, and an e2e test of the dialog (the e2e build has no Firebase settings, so it shows the link).
22. **Licences.** The `@firebase/*` packages are Apache-2.0 but ship no licence file, so the M7-3 build step refused them. It now uses the standard Apache-2.0 text (`webapp/scripts/licences/Apache-2.0.txt`, copied from TypeScript's) for packages that declare Apache-2.0 without a file.
23. **CI.** `functions-ci.yml` checks the function. Nothing deploys it: the CI service account has Hosting roles only (M0-23). But Hosting deploys with a function rewrite look the function up, and GitHub issue threads on `action-hosting-deploy` report 403s without Cloud Functions and Cloud Run viewer roles. Owner step 5.1 grants `roles/cloudfunctions.viewer` and `roles/run.viewer` (anecdotal, not in Firebase's docs).
24. **Our own one-use check on App Check tokens** (2026-11-23). The first production smoke test (owner part 7) found a replayed token accepted. Testing with a debug token against the live function, with bodies that fail validation so no issue could result: a **limited-use token's second use was accepted 9 times in 20**, whatever the gap (0 to 20 seconds); a **session token** (one hour) **was never marked as used**. App Check is enforced (no token gets 401), and `verifyToken(token, { consume: true })` is called correctly; it's App Check's consumption that misses. Firebase's docs describe neither behaviour. So the function now records every verified token's `jti` in Firestore, `usedAppCheckTokens/{jti}` (`usedAt`, `expireAt` = the token's expiry, TTL policy in owner step 4.4), with a create-only write: a second use of any token gets 401 (`app_check_replayed` in the logs), even when two requests race (checked in the Firestore emulator). App Check's own check stays as a first layer. If Firestore can't be written, the function refuses the report (503 `unavailable`) rather than risk a replay. The token is used up before validation, so a report that fails validation can't be resent with it; the web app fetches a new token for every Send anyway. Cost: one Firestore write per report.
25. **X-Forwarded-For, tested and fixed** (2026-11-23 to 25). Through Hosting (`meridian.blueanvildesigns.io/api/report-bug`), a client's made-up X-Forwarded-For didn't become the first entry, but at the function's own URLs (`…cloudfunctions.net/reportBug`, `reportbug-…run.app`), which skip Hosting, it did: each made-up address got its own 5 an hour. Logging the raw headers of one forged request each way (2026-11-25, logging removed since) showed why. Google's front end *appends* the address it received the request from: at the function's own URL that's the caller (`<forged>,<caller>`). Hosting *replaces* the visitor's header with the visitor's real address (the forged value moves to `fastly-temp-xff`), and the front end then appends Hosting's own address (`<visitor>,192.178.11.103`). **No header proves a request came through Hosting:** `via: 1.1 Firebase Hosting`, `fastly-client-ip`, `x-forwarded-host`, `x-firebase-hosting-channel` and the rest are ordinary headers a direct caller can send too, and Hosting can't add a secret one. So the function can't refuse direct calls; instead `clientAddress` walks X-Forwarded-For from the right, skips Hosting's addresses, and keys on the first other one. Hosting's requests arrived from 66.102.0.0/20, 74.125.0.0/16 and 192.178.0.0/15 (17 of 17 seen over three days); all three are Google's own ranges and none is a Google Cloud customer range, so nobody can rent a machine there to pose as Hosting. Loopback is skipped too, for the Hosting emulator. If Hosting starts arriving from another range, its visitors share that address's limit: stricter, never looser. Verified after deploy: see the PR (fix/report-bug-direct-url).
